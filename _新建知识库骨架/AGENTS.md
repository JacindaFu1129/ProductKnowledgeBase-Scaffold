# <产品> <业务线> · 业务知识工作台

> 这是用「业务知识库脚手架」创建的实例。本文件即该库的操作规范（自包含）。
> 新建后请把本文件里的 `<产品>` `<业务线>` `<模块…>` 等占位符替换为实际名称。

## 这是什么
本目录是 <产品>「<业务线>」的**业务知识工作台**。**核心资产是一套可持续维护的业务知识库**；讲解 HTML 等只是"按需生成的临时视图"。

## 核心定位：核心资产 vs 按需产出（最重要）
```
业务认知/ + 变更记录.md   = 长期核心资产（唯一维护对象）
        │ 按需生成（临时视图/快照，用完可丢、可重生）
        ▼
产出/  ── 讲解HTML · 跨业务说明 · 交接清单 · 回溯报告 …
```
- **只维护知识库**；`产出/` 不长期维护，需要时从知识库重生。
- 知识库要撑起 4 类用途：①版本迭代设计咨询 ②跨业务说明 ③新人交接 ④历史问题回溯。前两类靠 `变更记录.md` + 溯源，后两类靠 模块 MD + 总览心智模型。

## 目录约定
| 目录/文件 | 作用 | 规则 |
|---|---|---|
| `业务认知/<模块>.md` | ★**知识库·唯一事实来源**，按模块的活文档 | 跨版本累积；对齐 <业务线> 菜单命名 |
| `业务认知/00_总览.md` | 整体地图、菜单结构、通用心智模型 | 菜单/定位变化时更新 |
| `业务认知/_模块模板.md` | 新建模块时复制它改名 | 不直接写内容 |
| `变更记录.md` | ★**版本时间线**：版本/需求号/模块/变更点/原因/溯源 | 每次版本迭代**追加一行** |
| `索引.md` | 现状索引（模块×设计稿×版本×需求号×提取状态） | **每次开工先读它** |
| `设计源/v<X.Y>/<模块>/*.png` | 原始画板导出，供溯源 | **只增不改**；命名 `模块-特性（需求号）.png` |
| `产出/` | **按需生成的临时快照**（讲解HTML等） | 不长期维护，可清空；每个产物注明用途/日期/来源 |
| `工具/切片.ps1` | 长图切片脚本（UTF-8 BOM） | 产物进 `_临时/` |
| `_临时/` | 切片等中间产物 | 可随时删 |

## ★ 业务认知 vs 变更记录：写什么、不写什么（最重要的内容原则）
两类文件分工严格，**不要混**。

### `业务认知/<模块>.md` = 概念，不是需求清单
只写**不随版本变的业务知识**。一篇合格的业务认知应含（不必每项都有，顺序如下）：
1. **一句话定位**：这个模块是什么、为什么存在。
2. **核心流程 / 链路**：主流程怎么跑。区分**配置链路**（管理员怎么搭：可绑定哪些设备、各设备什么能力、几步配完）与**应用链路**（运行时怎么服务用户）——很多模块只讲了应用、漏了配置。
3. **核心概念**：关键实体、分类与相互关系。
4. **规则的本质**：规则**为什么**这么定，而不是具体取值/字段。
5. **心智模型 / 一句话**：把上面压缩成一句能记住的话。
6. **FAQ**：阅读者真正会问的问题。

- **不写**版本号、不复述单条需求、不罗列具体交互（提示文案、按钮二次确认、控件默认值、字段级 UI）。
- 判断标准：读完能回答**阅读者/提问者**问的"是什么/为什么/怎么跑"，而不是"这个版本改了哪些点"。

### `变更记录.md` = 需求与版本细节
谁在哪个版本、因哪个需求号、改了什么交互、为什么、影响——全进这里。业务认知里需要时写"具体交互见 `变更记录.md`"。

> 一句话：**业务认知回答"是什么/为什么/怎么跑"，变更记录回答"哪个版本改了什么"。**

## 设计源放什么：源分层与冲突处理
`设计源/` 收两类一手依据（**只增不改，供溯源**）：
- **认知基础**：技术白皮书 / 早期基线文档，最适合喂业务认知。
- **增量设计稿 / 真实环境截图**：各版本画板与产品截图。

**冲突处理**：以**较新的现状**为准；基线与现状明确不一致时**不改业务认知**，在 `00_总览.md` 存疑区登记待澄清；基线只用于填补空白。画板与环境截图冲突时，概念以真实环境为准。

## 标准工作流（人 + AI）
1. **人**：把新增/改动的画板或环境截图放进 `设计源/`，告知 AI。
2. **AI**：读 `索引.md` → 只对未提取或有变更的图切片、读图。
3. **AI**：概念写进 `业务认知/<模块>.md`；`变更记录.md` 追加条目（含需求号、原因、设计源）。
4. **AI**：更新 `索引.md` 状态。
5. 需要时 **AI** 从知识库按需生成到 `产出/`。

## 省 token 铁律
1. **图只读一次**：索引标「✅已提取」的不再读图；仅设计变更时重读。
2. **下游只读知识库**：出产出、答问答、更新，一律基于文本，不重扫全盘、不重读图。
3. **开工先读 `索引.md`**。
4. **产出是快照**：不手工长期维护，需要就重生；不放进 `业务认知/`。

## 命名与版本
- **模块**对齐 <业务线> 实际菜单（回填 `00_总览.md`）。
- 业务认知 MD **按模块命名，不按版本**。
- 设计稿文件名保留**需求号**。

## 切片脚本用法（PowerShell）
```powershell
工具\切片.ps1 -Src "设计源\v<X.Y>\<模块>" -Name "<模块>_v<X.Y>"
```
读图时读 `_临时/tiles/<Name>/<画板>__NN.png`（全宽纵向切片，1x 源，清晰可读）。

## 版本管理（Git / GitLab）
用 git 做版本管理时，**只上传知识核心，派生物与大素材不上传**（见 `.gitignore`）：
- ✅ **入库**：`AGENTS.md`、`索引.md`、`变更记录.md`、`业务认知/*.md`、`工具/`、`.gitignore`——纯文本、是资产，别人拉的就是这些。
- ❌ **不入库**：`_临时/`（切片，可重生）、`产出/` 的生成物（留 README，其余可重生）。
- ⚠️ **设计源**（最大）：知识已提取进 `业务认知/`，纯读知识库的人无需拉取。二选一：
  - **方案A（默认）**：`.gitignore` 掉，素材放共享盘/对象存储，靠 `变更记录` 的需求号+文件名追溯。
  - **方案B**：要在仓库里可追溯，用 **Git LFS** 跟踪 `设计源/`，别人可 `GIT_LFS_SKIP_SMUDGE=1` 跳过下载。
- **节奏**：版本变更时做一次"归档提取"（新素材入 `设计源/` → 提取 → 更新知识库），再提交推送。
- **注意**：首次提交前就放好 `.gitignore`；素材若已被提交过，需 `git rm -r --cached` 并（必要时）清历史，否则仓库仍会很大。
